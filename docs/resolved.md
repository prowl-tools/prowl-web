### ~~PQW-006: Make the nav Products dropdown keyboard/screen-reader accessible~~
**Resolved**: 2026-08-09 (commit fbd0efa, branch: nav-ally-docs-h1)
**Description**: The desktop Products dropdown in `src/components/Nav.tsx` was CSS-hover/`group-focus-within` only — the trigger had no `aria-expanded`/`aria-controls`, no click or keyboard handler, no Escape-to-close, and defaulted to `type="submit"`, failing WCAG 2.1 SC 4.1.2 (Name, Role, Value) and 1.4.13 (Content on Hover or Focus). Converted it to a JS-controlled disclosure following the WAI-ARIA APG **disclosure** pattern (deliberately not the full ARIA `menu` widget): managed open state, trigger is `type="button"` with `aria-expanded` + `aria-controls` pointing at the menu region, toggles on click/Enter/Space (native button activation), and is dismissible via Escape (returning focus to the trigger), outside pointer press, and focus leaving the container — it also closes when a menu item is selected. Visibility is driven by React state so the menu links are only in the tab order while open, while hover-to-open is preserved for mouse users (no pointer-UX regression). Open/close decision logic is extracted to a DOM-free `src/lib/disclosure.ts` (`disclosureReducer`, `isDismissKey`, `shouldCloseOnFocusOut`) with 5 `node:test` unit tests. The `nav-desktop` hunt was updated in lockstep (the old `aria-haspopup`/`.group` selectors were removed) and extended to assert the disclosure contract: collapsed on load, `aria-expanded` flips true on hover-open, and clicking the trigger toggles it back to false. Verified: lint + build green; `npm test` 15/15; full hunt suite green (nav-desktop 13/13) and mobile hunt suite green (nav-mobile 7/7); homepage still exposes exactly one `<h1>` and no `aria-haspopup`.
